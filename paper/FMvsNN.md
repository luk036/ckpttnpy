# FM vs NN — With/Without Multilevel, Bi & K-way Partitions

## 1. Overview

This report compares the two refinement operators of `ckpttn`:

- **FM** — Fiduccia–Mattheyses: gain-bucket pass with snapshot/rollback and
  per-move vertex locking (`PartMgrBase` / `FMPartMgr`).
- **NN** — *No-Nonsense*: a pure greedy local search that takes the
  highest-gain move while its gain is positive, with **no** snapshotting,
  rollback or locking (`NNPartMgr`).

Each is measured **flat** (single-level) and inside the **multilevel** (ML)
framework, for **bi-partitioning** (k = 2) and **k-way partitioning** (k = 3),
giving the 8 configurations below. Three ports are covered: the Python
reference implementation (`ckpttnpy`), the C++ port (`ckpttn-cpp`) and the
Rust port (`ckpttn-rs`).

## 3. Methodology

- **Testcases**: `p1` (833 modules, 902 nets) and `ibm03` (23,136 modules,
  27,401 nets, IBM-PLACE format).
- **Seeds**: 0–4 (5 runs per configuration).
- **Initial partition**: generated by a SplitMix64 PRNG with the seed, one
  draw per module index (`part[i] = next() % k`). The generator is identical in
  Python, C++ and Rust so a seed denotes the same assignment.
- **Parameters**: `bal_tol = 0.45`; multilevel `limitsize = 50` (contraction is
  attempted whenever `num_modules >= limitsize`).
- **Metrics**:
  - *cut cost* — reported as **best** and **mean** over the 5 seeds;
  - *runtime* — wall-clock, reported as **median** over the 5 seeds (robust to
    scheduling noise). A single Python outlier is documented in §7.
- **Harnesses**: `benchmarks/compare_fm_nn.py` (Python),
  `bench/BenchFMNN.cpp` + xmake target `bench_fmnn` (C++), and
  `examples/fmnn_compare.rs` (Rust, release build).

## 6. Findings

1. **FM dominates NN on quality; NN dominates FM on speed — in all three
   ports.** Flat NN is 1.6–2.8× worse in cut cost but 10–100× faster
   (e.g. flat bi on ibm03: 0.06 s vs 2.7 s in Rust; 0.40 s vs 10.3 s in C++;
   1.2 s vs 13.0 s in Python).

2. **Multilevel helps both, and helps NN the most.** Coarsening reduces the cut
   by 12–62 %. Without ML, NN is a weak standalone heuristic; with ML it
   recovers much of FM's quality (flat NN 220 → ML NN 108 on p1; flat NN 7271 →
   ML NN 3922 on ibm03; Rust: flat NN 225 → ML NN 157 on p1). This is precisely
   the intended role of a cheap "pure local search" refiner inside the
   multilevel loop.

3. **FM + ML gives the best quality** in every configuration and every port.
   NN + ML remains ~1.3–3.5× worse but is considerably cheaper.

4. **Runtime**: ML is much slower than flat (coarsening + recursion overhead),
   and k-way (k = 3) is slower than bi. C++ is roughly 5–50× faster than Python
   overall; the Rust release build is fastest of the three (e.g. ibm03 k = 3 FM
   ML: 13.3 s vs 80 s C++ / 265 s Python; ibm03 NN+ML: 0.5–0.6 s).

5. **The Rust NN+ML rows trail the reference ports by ~30 %** (e.g. p1 Bi NN-ML:
   157 vs 108 py / 86 cpp). The equal-key pops and the graph adjacency order
   differ between `ckpttn-rs` (petgraph edge-insertion order) and the
   reference, so the greedy NN walks a different path to a nearby local optimum.
   FM rows and flat-NN rows track Python/C++ closely, which confirms the gain
   bookkeeping itself is correct after the re-port (see §9).

## 7. Caveats and data quality

- **Python runtime outlier (resolved).** One run — p1, k = 2, FM, ML, seed 2 —
  recorded 3355 s in the first (background) sweep while all other seeds took
  ~1 s. Re-measured in isolation it takes **0.99 s** (same cut cost 56), i.e. the
  reading was a scheduling artifact (the unattended background process was
  starved/suspended), **not** a code defect. The p1 data was re-collected and
  the tables above use the clean values; medians are used throughout to keep
  runtimes robust.

- **Cross-language comparability.** Python, C++ and Rust each order the graph
  slightly differently when loading, so per-seed results are not bit-identical;
  the intra-language trends are the signal. Python vs C++ vs Rust wall-clock is
  inherently not directly comparable (interpreted vs compiled).

- **Variability.** Cut cost varies with the random start; the `best` and `mean`
  columns should both be read. NN + ML is the most sensitive to the start.

- **Rust NN+ML residual.** The Rust `NN+ML` rows are ~30 % worse than the
  reference ports because `ckpttn-rs` builds the netlist adjacency from
  petgraph edge-insertion order and its bucket queue pops the most-recent
  equal-key entry, whereas Python/C++ differ on both counts — the greedy search
  therefore converges to a different (nearby) local optimum. All FM and flat-NN
  rows match the reference, so the gain bookkeeping is not at fault (see §9).

## 9. Rust port status

The Rust port (`ckpttn-rs`) is now included. Its initial harness run surfaced a
series of defects in the multilevel pipeline; all were fixed on `dev` in commit
`c25b69d` (`fix: align gain managers with FM semantics (fixes #23)`):

- **Duplicate module–net edges** in `HierNetlist::add_edge` made
  `degree(net)` disagree with `neighbors(net).count()` (panic in
  `update_move_3pin_net`); a dedup guard was added.
- **Stale gain buckets**: `BucketQueue` tracked a single `current_max` with no
  live-entry bookkeeping, so popped keys were re-selected (and, worse, the
  multilevel harness looped forever on ibm03).
- **Wrong `modify_key` semantics**: the FM manager wrote an absolute key from a
  delta and targeted the wrong bucket; `set_key` had insert side effects.
- **ML collapse to cut 0**: `FMConstrMgr::update_move` used a stale
  `weight_cache` (never set by `check_constraints`), so balance constraints
  were ignored during multilevel refinement.
- **k-way 3-pin nets** were missing the `weight = -weight` sign flip in
  `FMKWayGainCalc::update_move_3pin_net` (matches the C++ port).
- **`HierNetlist::get_max_degree`** ignored net weights, shrinking the bucket
  range on contracted graphs.

Verification after the fix: `cargo test` **245 passed, 0 failed**, clippy
clean, and the harness completes 80 records. A regression test
(`test_ml_bi_part_mgr_dwarf`) asserts the dwarf bi-ML result cost is `> 0`.

The Rust column was produced with the same SplitMix64 seeds as Python and C++.
The only residual divergence — the ~30 % gap in the NN+ML rows — is a
search-path effect (equal-key pop order and graph adjacency order), not a gain
bookkeeping defect, as the FM rows match the reference ports.
